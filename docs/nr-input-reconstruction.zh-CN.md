# NR 视频输入重建：接口边界与方案对照

[English](nr-input-reconstruction.en.md) · 简体中文

Audience: public

2026-09-03。当前已实现可连接的 DIS / NVIDIA 光流 provider、缓存及诊断。
下文的深度、分割和外部 MASK 契约是扩展注意事项，不表示已实现或传入 NR。

## 先区分三件事

1. **游戏引擎拥有什么**：几何、材质、相机变换、深度、逐像素运动、
   UI 分层等可用于不同渲染阶段的数据。
2. **NR 推理实际需要什么**：NVIDIA 9 月 1 日的研究说明列出当前画面、
   引擎运动向量、延续的时序状态和艺术控制。训练中的场景属性监督，
   不等于运行时必须喂入完整 G-buffer。
3. **本项目能传什么**：现有外部 worker 的 D5V2 契约只传 RGBA8 画面、
   RG16_FLOAT 运动、逐帧索引/时间戳/reset 和 Look 参数；没有深度或
   外部控制蒙版平面。闭源 worker 内部是否创建占位纹理不能由协议推定。

官方资料：[NVIDIA ADLR：DLSS 5](https://research.nvidia.com/labs/adlr/DLSS5/)、
[9 月 1 日技术介绍与艺术控制](https://www.nvidia.com/en-eu/geforce/news/dlss-5-3d-guided-neural-rendering/)。
这些描述不能自动当作当前实验性 RTX40 worker/DLL 的完整 ABI。

SR 和 FG 另有输入要求：SR 的资源包含深度、运动、输入/输出颜色；FG 也
使用深度和运动，并推荐独立的无 UI 画面及 UI 数据。不要把这些要求整套
套在当前 NR 上。参考 [SR 集成指南](https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuideDLSS.md)
与 [FG 集成指南](https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuideDLSS_G.md)。

## 输入、替代来源与当前状态

| 信息 | 视频侧获取方式 | 当前状态 / 后续用途 |
| --- | --- | --- |
| 颜色、尺寸、时间轴 | 原视频解码；明确色彩解释，保留裁剪/时间戳 | 已使用；当前 SDR RGBA8，不能冒充 HDR 或恢复丢失细节 |
| 当前像素在上一帧的位置 | 稠密光流，保留相机运动和动态物体运动 | 已有 DIS / NVIDIA provider，保留零向量诊断模式 |
| 连续时序与历史重置 | 连续顺序处理、真实前置帧、镜头切换与跳帧检测 | 已有 pre-roll、warmup 和简单切镜 reset；仍需改进检测 |
| 光流可信度、遮挡、新显露区域 | 双向一致性、越界、重投影误差，未来可辅以深度 | 当前仅有诊断统计，没有逐像素置信图传给 NR |
| 艺术控制蒙版 | 人脸/皮肤/字幕等分割、手绘 MASK、跨帧跟踪 | 当前没有外部蒙版传输；未来需明确方向和实际作用，不等于自动遮罩 |
| 深度 | 相对/逆深度或尺度深度估计，优先考虑视频时序一致性 | 当前不能传；可先研究它对引导质量的帮助，再验证运行时是否消费 |
| 法线、材质、相机标定 | 从 RGB 估计只能得近似值，且通常不唯一 | 不作为当前 NR 的必做输入；按实际后端需求再评估 |

光流不是引擎几何运动的等价替代。遮挡处、反射、透明、运动模糊、重复纹理
和生成视频本身的形变都可能让对应关系不可靠。不能通过“光流更大”或伪造
运动让 NR 更强；目标是正确的跨帧对应。

白膜可视化不是深度数值本身。单帧相对深度不保证物理尺度或逐帧尺度一致，
也不能单凭一张深度图算出动态物体的运动。若后端需要设备 Z，必须明确深度
约定及必要的投影参数；不能把 0–1 的灰度随意命名为真实相机深度。

DLSS-COM 的 README（本地参考提交 3aeca71）报告了一个有价值的负结果：
其当前模型对不同深度纹理得到相同输出，而控制蒙版有响应。
这是该项目/版本的观察，不是所有 NR DLL 都忽略深度的证明。
来源：[项目深度说明](https://github.com/MYT-YEP/DLSS-COM#%E6%B7%B1%E5%BA%A6%E5%9B%BE%E4%B8%BA%E4%BB%80%E4%B9%88%E6%B2%A1%E6%9C%89%E6%98%8E%E6%98%BE%E5%8F%98%E5%8C%96)。

## 提议的统一引导契约

不把算法名称绑定到 worker。不同 provider 输出统一的、可独立缓存的引导包：

- **共同元数据**：来源视频指纹、裁剪窗口、逐帧 PTS、帧尺寸、缩放/填充、
  provider/模型/版本/参数、计算精度、有效区域、来源是原生还是估计。
- **运动**：每帧 H×W×2 浮点数，当前→上一帧，左上角原点，x 向右/y 向下，
  本帧尺寸下的像素位移。首帧/切镜明确 reset。不能只给彩色光流预览图。
  前向流不能简单取负当反向流；切换算法时必须做坐标和对应方向适配。
- **置信/遮挡**：H×W 的有效性或可信度，声明 0/1 含义、越界及未知值。
  不要将重建置信度直接等同于艺术增强控制蒙版。
- **可选深度**：H×W 浮点数；声明 depth/逆深度、近远方向、单位、是否仅相对、
  无效值及跨帧归一化方式。避免逐帧独立 min/max 归一化引入尺度跳动。
- **可选效果蒙版**：与颜色严格对齐的 H×W 数值，声明增强/保护方向及羽化。
  后合成混合可以独立实现，但必须标为后合成，不能声称已影响 NR 内部推理。

后端按能力挑选可消费的平面，节点报告必须区分：**已生成 / 已传入 / 已确认
影响输出**。不支持的选项要报清楚，不能接上线后静默丢弃。

## 节点职责与扩展边界

- Video Input Adapter：媒体兼容性、色彩解释、输入信息，保持轻量检查。
- Video Guides：算法选择和统一引导包；当前连接独立光流 provider。
  深度、MASK provider 需要新契约，不是当前可接入的节点。
- 引导诊断：可视化光流/深度/可信度、切镜和重投影误差，不把误差当审美评分。
- NR Look：只管画面风格与强度；Preview / Process 消费同一组引导和 Look。

增加深度支持前，应先测试无深度/常量深度/估计深度/扰乱深度，再决定是否
扩展或更换 worker。传输扩展需要显式版本/能力协商，不向现有 D5V2 流追加字节。
任何新增平面都计入内存/磁盘预算。预览只计算选中范围及算法必要上下文；
换 Look 不重新计算引导，换模型/裁剪/尺度必须使对应缓存失效。

## 对照候选项目时需要的信息

接入新的 provider 时，维护者需要核对以下信息：

1. 光流/深度/分割/跟踪哪个任务；是现有 Comfy 节点、Python 库还是独立程序。
2. 输入输出的数值格式、方向/尺度、帧顺序，能否导出原始浮点场。
3. 单帧/双帧/整段视频处理，是否需未来帧、分块重叠和固定分辨率。
4. 视频时序稳定性，有无置信度/遮挡输出；深度是否尺度稳定。
5. Linux、CUDA/PyTorch/ONNX 等依赖，权重体积、显存及速度，是否会冲突现有环境。
6. 代码及权重许可，下载方式；默认不自动安装或打包第三方内容。

用户的选择主要是：更重视速度还是稳定性/细节、预期分辨率和视频长度，以及
可接受的额外显存/模型体积。其余接口细节不应变成用户接线的负担。
